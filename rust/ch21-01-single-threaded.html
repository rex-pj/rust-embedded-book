Xây dựng web server đơn luồng

Chúng ta sẽ bắt đầu bằng việc làm cho một web server đơn luồng chạy được. Trước khi bắt đầu, hãy điểm nhanh qua các giao thức liên quan tới việc xây dựng web server. Chi tiết của những giao thức này nằm ngoài phạm vi cuốn sách, nhưng một cái nhìn tổng quan ngắn gọn sẽ cho bạn đủ thông tin cần thiết.

Hai giao thức chính liên quan tới web server là Hypertext Transfer Protocol (HTTP) và Transmission Control Protocol (TCP). Cả hai đều là giao thức request-response, nghĩa là một client khởi tạo request, còn một server lắng nghe các request đó và trả về response cho client. Nội dung của những request và response ấy do chính các giao thức quy định.

TCP là giao thức ở tầng thấp hơn, mô tả chi tiết cách thông tin đi từ server này sang server khác nhưng không quy định thông tin đó là gì. HTTP xây dựng bên trên TCP bằng cách định nghĩa nội dung của request và response. Về mặt kỹ thuật, có thể dùng HTTP với các giao thức khác, nhưng trong đại đa số trường hợp, HTTP gửi dữ liệu của nó qua TCP. Chúng ta sẽ làm việc trực tiếp với các byte thô của request và response TCP và HTTP.

📌
Sơ đồ: Luồng xử lý Server Đơn luồng

Single-threaded server flow:
TCP Listener → Nhận stream → handle_connection() → Đọc HTTP request → Trả về HTTP response → Đóng kết nối → (lặp lại — xử lý tuần tự)

Hạn chế: Mỗi lần chỉ xử lý được 1 request. Nếu một request chậm, toàn bộ các request sau phải chờ.

Lắng nghe kết nối TCP

Web server của ta cần lắng nghe một kết nối TCP, nên đó là phần đầu tiên ta bắt tay vào. Thư viện chuẩn cung cấp module std::net để làm việc này. Hãy tạo một dự án mới theo cách quen thuộc:

$ cargo new hello
     Created binary (application) `hello` project
$ cd hello

Giờ hãy nhập đoạn mã ở Listing 21-1 vào src/main.rs để bắt đầu. Đoạn mã này sẽ lắng nghe các TCP stream đến tại địa chỉ cục bộ 127.0.0.1:7878. Khi nhận được một stream đến, nó sẽ in ra Connection established!.

Dùng TcpListener, ta có thể lắng nghe các kết nối TCP tại địa chỉ 127.0.0.1:7878. Trong địa chỉ này, phần trước dấu hai chấm là một địa chỉ IP đại diện cho máy tính của bạn (địa chỉ này giống nhau trên mọi máy tính, không phải máy của tác giả), còn 7878 là cổng. Ta chọn cổng này vì hai lý do: HTTP thường không được chấp nhận trên cổng này, nên server của ta ít khả năng xung đột với web server nào khác đang chạy trên máy bạn; và 7878 chính là chữ rust bấm trên bàn phím điện thoại.

Hàm bind trong trường hợp này hoạt động giống hàm new, tức là nó trả về một instance TcpListener mới. Hàm được đặt tên bind vì trong mạng máy tính, việc kết nối tới một cổng để lắng nghe được gọi là “binding tới một cổng”.

Hàm bind trả về một Result<T, E>, cho thấy việc bind có thể thất bại — ví dụ nếu ta chạy hai instance của chương trình và như vậy có hai chương trình cùng lắng nghe một cổng. Vì đang viết một server cơ bản chỉ để học, ta sẽ không bận tâm xử lý những lỗi kiểu này; thay vào đó ta dùng unwrap để dừng chương trình nếu có lỗi.

Phương thức incoming trên TcpListener trả về một iterator cho ta một dãy các stream (cụ thể hơn là các stream kiểu TcpStream). Một stream đại diện cho một kết nối đang mở giữa client và server. Connection là tên gọi cho toàn bộ quá trình request và response, trong đó client kết nối tới server, server sinh ra response, rồi server đóng kết nối. Như vậy, ta sẽ đọc từ TcpStream để xem client đã gửi gì, rồi ghi response của mình vào stream để gửi dữ liệu ngược lại cho client. Nhìn chung, vòng for này sẽ xử lý lần lượt từng kết nối và tạo ra một loạt stream để ta xử lý.

Hiện tại, việc xử lý stream của ta chỉ gồm gọi unwrap để kết thúc chương trình nếu stream có lỗi; nếu không có lỗi, chương trình in ra một thông báo. Ta sẽ thêm chức năng cho trường hợp thành công ở listing tiếp theo. Lý do ta có thể nhận lỗi từ phương thức incoming khi một client kết nối tới server là vì thực ra ta không lặp trên các kết nối, mà lặp trên các lần thử kết nối. Việc kết nối có thể không thành công vì nhiều lý do, phần lớn phụ thuộc hệ điều hành. Chẳng hạn, nhiều hệ điều hành giới hạn số kết nối mở đồng thời mà chúng hỗ trợ; những lần thử kết nối vượt quá con số đó sẽ sinh lỗi cho tới khi một số kết nối đang mở được đóng lại.

Hãy thử chạy đoạn mã này! Gọi cargo run trong terminal rồi tải 127.0.0.1:7878 trên trình duyệt. Trình duyệt sẽ báo lỗi kiểu “Connection reset”, vì server hiện chưa gửi lại dữ liệu nào. Nhưng khi nhìn vào terminal, bạn sẽ thấy vài thông báo được in ra lúc trình duyệt kết nối tới server!

     Running `target/debug/hello`
Connection established!
Connection established!
Connection established!

Đôi khi bạn sẽ thấy nhiều thông báo được in ra cho một request từ trình duyệt; lý do có thể là trình duyệt vừa yêu cầu trang, vừa yêu cầu những tài nguyên khác, chẳng hạn biểu tượng favicon.ico hiện trên tab trình duyệt.

Cũng có thể là trình duyệt đang cố kết nối tới server nhiều lần vì server không phản hồi dữ liệu nào. Khi stream ra khỏi scope và bị drop ở cuối vòng lặp, kết nối bị đóng như một phần của phần triển khai drop. Trình duyệt đôi khi xử lý kết nối bị đóng bằng cách thử lại, vì vấn đề có thể chỉ là tạm thời.

Trình duyệt đôi khi cũng mở nhiều kết nối tới server mà không gửi request nào, để nếu sau đó nó có gửi request thì những request ấy diễn ra nhanh hơn. Khi điều này xảy ra, server của ta sẽ thấy từng kết nối, bất kể có request nào trên kết nối đó hay không. Chẳng hạn nhiều phiên bản trình duyệt nền Chrome làm vậy; bạn có thể tắt tối ưu hóa đó bằng cách dùng chế độ duyệt web riêng tư hoặc dùng trình duyệt khác.

Điều quan trọng là ta đã lấy được một handle tới kết nối TCP!

Nhớ dừng chương trình bằng cách bấm ctrl-C khi đã chạy xong một phiên bản mã cụ thể. Rồi khởi động lại chương trình bằng lệnh cargo run sau mỗi lần thay đổi mã, để chắc chắn bạn đang chạy mã mới nhất.

Đọc request

Hãy triển khai chức năng đọc request từ trình duyệt! Để tách bạch hai mối quan tâm — trước hết là lấy được kết nối, sau đó là làm gì đó với kết nối — ta sẽ tạo một hàm mới để xử lý kết nối. Trong hàm handle_connection mới này, ta sẽ đọc dữ liệu từ TCP stream và in ra để xem trình duyệt gửi những gì. Hãy sửa mã thành như Listing 21-2.

Ta đưa std::io::BufReader và std::io::prelude vào scope để dùng được những trait và kiểu cho phép đọc từ stream và ghi vào stream. Trong vòng for ở hàm main, thay vì in thông báo cho biết đã tạo được kết nối, giờ ta gọi hàm handle_connection mới và truyền stream cho nó.

Trong hàm handle_connection, ta tạo một instance BufReader mới bọc quanh một tham chiếu tới stream. BufReader bổ sung khả năng đệm bằng cách quản lý giúp ta những lời gọi tới các phương thức của trait std::io::Read.

Ta tạo một biến tên http_request để thu thập các dòng của request mà trình duyệt gửi tới server. Ta cho biết mình muốn thu thập những dòng này vào một vector bằng cách thêm chú thích kiểu Vec<_>.

BufReader triển khai trait std::io::BufRead, trait này cung cấp phương thức lines. Phương thức lines trả về một iterator các Result<String, std::io::Error> bằng cách tách dòng dữ liệu mỗi khi gặp một byte xuống dòng. Để lấy từng String, ta dùng map và unwrap trên từng Result. Result có thể là lỗi nếu dữ liệu không phải UTF-8 hợp lệ, hoặc nếu có trục trặc khi đọc từ stream. Một lần nữa, chương trình dùng thật nên xử lý những lỗi này khéo léo hơn, nhưng ở đây ta chọn dừng chương trình khi có lỗi cho đơn giản.

Trình duyệt báo hiệu kết thúc một HTTP request bằng cách gửi hai ký tự xuống dòng liên tiếp; vậy nên để lấy một request từ stream, ta nhận các dòng cho tới khi gặp một dòng là chuỗi rỗng. Sau khi đã thu thập các dòng vào vector, ta in chúng ra bằng định dạng debug đẹp mắt để xem trình duyệt web đang gửi những chỉ dẫn gì tới server.

Hãy thử đoạn mã này! Khởi động chương trình rồi lại gửi một request từ trình duyệt. Lưu ý rằng trình duyệt vẫn sẽ hiện trang báo lỗi, nhưng kết quả in ra terminal của chương trình giờ sẽ giống thế này:

Tùy trình duyệt, kết quả bạn nhận được có thể hơi khác. Giờ khi đã in ra dữ liệu request, ta có thể hiểu vì sao một request từ trình duyệt lại sinh ra nhiều kết nối, bằng cách nhìn vào đường dẫn sau GET ở dòng đầu của request. Nếu những kết nối lặp lại đó đều yêu cầu /, ta biết trình duyệt đang cố lấy / nhiều lần vì nó không nhận được phản hồi nào từ chương trình.

Hãy mổ xẻ dữ liệu request này để hiểu trình duyệt đang yêu cầu chương trình của ta điều gì.

Xem xét kỹ hơn một HTTP request

HTTP là giao thức dạng văn bản, và một request có định dạng như sau:

Method Request-URI HTTP-Version CRLF
headers CRLF
message-body

Dòng đầu tiên là request line, chứa thông tin về thứ mà client đang yêu cầu. Phần đầu của request line cho biết method đang dùng, chẳng hạn GET hay POST, mô tả cách client tạo request này. Client của ta dùng request GET, nghĩa là nó đang hỏi xin thông tin.

Phần tiếp theo của request line là /, cho biết uniform resource identifier (URI) mà client đang yêu cầu: URI gần giống, nhưng không hẳn giống, uniform resource locator (URL). Khác biệt giữa URI và URL không quan trọng với mục đích của chương này, nhưng đặc tả HTTP dùng thuật ngữ URI, nên ta cứ ngầm hiểu URL thay cho URI ở đây.

Phần cuối là phiên bản HTTP mà client dùng, rồi request line kết thúc bằng một chuỗi CRLF. (CRLF là viết tắt của carriage return và line feed, những thuật ngữ từ thời máy đánh chữ!) Chuỗi CRLF cũng có thể viết là \r\n, trong đó \r là carriage return còn \n là line feed. Chuỗi CRLF ngăn cách request line với phần dữ liệu còn lại của request. Lưu ý rằng khi CRLF được in ra, ta thấy một dòng mới bắt đầu chứ không thấy \r\n.

Nhìn vào dữ liệu request line ta nhận được từ chương trình đến giờ, ta thấy GET là method, / là request URI, và HTTP/1.1 là phiên bản.

Sau request line, những dòng còn lại bắt đầu từ Host: trở đi là các header. Request GET không có body.

Hãy thử gửi request từ một trình duyệt khác, hoặc yêu cầu một địa chỉ khác như 127.0.0.1:7878/test, để xem dữ liệu request thay đổi ra sao.

Giờ đã biết trình duyệt đang yêu cầu gì, hãy gửi lại một ít dữ liệu!

Viết response

Ta sẽ triển khai việc gửi dữ liệu để phản hồi request của client. Response có định dạng như sau:

HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body

Dòng đầu tiên là status line, chứa phiên bản HTTP dùng trong response, một mã trạng thái dạng số tóm tắt kết quả của request, và một reason phrase mô tả bằng văn bản cho mã trạng thái đó. Sau chuỗi CRLF là các header (nếu có), thêm một chuỗi CRLF nữa, rồi tới body của response.

Đây là một response ví dụ dùng HTTP phiên bản 1.1, có mã trạng thái 200, reason phrase là OK, không có header và không có body:

HTTP/1.1 200 OK\r\n\r\n

Mã trạng thái 200 là phản hồi thành công tiêu chuẩn. Đoạn văn bản trên là một HTTP response thành công cực nhỏ. Hãy ghi nó vào stream để làm phản hồi cho một request thành công! Trong hàm handle_connection, hãy bỏ lệnh println! vốn in dữ liệu request và thay bằng đoạn mã ở Listing 21-3.

Dòng mới đầu tiên định nghĩa biến response giữ dữ liệu của thông báo thành công. Rồi ta gọi as_bytes trên response để chuyển dữ liệu chuỗi thành byte. Phương thức write_all trên stream nhận một &[u8] và gửi thẳng những byte đó qua kết nối. Vì thao tác write_all có thể thất bại, ta dùng unwrap cho mọi kết quả lỗi như trước. Một lần nữa, trong ứng dụng thật bạn sẽ phải thêm phần xử lý lỗi ở đây.

Với những thay đổi này, hãy chạy mã và gửi một request. Ta không còn in dữ liệu nào ra terminal nữa, nên sẽ không thấy kết quả gì ngoài phần in ra của Cargo. Khi tải 127.0.0.1:7878 trên trình duyệt, bạn sẽ thấy một trang trắng thay vì một lỗi. Bạn vừa tự tay viết mã nhận một HTTP request và gửi đi một response!

Trả về HTML thật

Hãy triển khai chức năng trả về thứ gì đó hơn một trang trắng. Tạo file mới hello.html ở thư mục gốc của dự án, không phải trong thư mục src. Bạn có thể viết bất kỳ HTML nào bạn muốn; Listing 21-4 là một khả năng.

Đây là một tài liệu HTML5 tối giản với một tiêu đề và ít văn bản. Để trả về nội dung này từ server khi nhận được request, ta sẽ sửa handle_connection như ở Listing 21-5: đọc file HTML, thêm nó vào response làm body, rồi gửi đi.

Ta đã thêm fs vào câu lệnh use để đưa module hệ thống tệp của thư viện chuẩn vào scope. Đoạn mã đọc nội dung một file thành chuỗi hẳn trông quen thuộc; ta đã dùng nó khi đọc nội dung file cho dự án I/O ở Listing 12-4.

Tiếp theo, ta dùng format! để thêm nội dung file vào làm body của response thành công. Để đảm bảo response HTTP hợp lệ, ta thêm header Content-Length, đặt bằng kích thước body của response — trong trường hợp này là kích thước của hello.html.

Chạy mã này bằng cargo run rồi tải 127.0.0.1:7878 trên trình duyệt; bạn sẽ thấy HTML của mình được render!

Hiện tại ta đang bỏ qua dữ liệu request trong http_request và cứ thế gửi lại nội dung file HTML bất kể thế nào. Nghĩa là nếu bạn thử yêu cầu 127.0.0.1:7878/something-else trên trình duyệt, bạn vẫn nhận về đúng response HTML đó. Lúc này server của ta còn rất hạn chế và chưa làm được điều mà hầu hết web server làm. Ta muốn tùy biến response tùy theo request, và chỉ gửi lại file HTML cho một request đúng chuẩn tới /.

Xác thực request và phản hồi có chọn lọc

Hiện tại, web server của ta sẽ trả về HTML trong file bất kể client yêu cầu gì. Hãy thêm chức năng kiểm tra rằng trình duyệt đang yêu cầu / trước khi trả về file HTML, và trả về lỗi nếu trình duyệt yêu cầu thứ khác. Muốn vậy ta cần sửa handle_connection như ở Listing 21-6. Đoạn mã mới này đối chiếu nội dung request nhận được với dạng request tới / mà ta đã biết, rồi thêm các khối if và else để xử lý các request khác nhau theo cách khác nhau.

Vì ta chỉ nhìn vào dòng đầu tiên của HTTP request, nên thay vì đọc toàn bộ request vào một vector, ta gọi next để lấy phần tử đầu tiên từ iterator. unwrap thứ nhất lo phần Option và dừng chương trình nếu iterator không có phần tử nào. unwrap thứ hai xử lý Result và có tác dụng giống unwrap nằm trong map đã thêm ở Listing 21-2.

Tiếp theo, ta kiểm tra request_line xem nó có bằng request line của một request GET tới đường dẫn / hay không. Nếu có, khối if trả về nội dung file HTML của ta.

Nếu request_line không bằng request GET tới đường dẫn /, nghĩa là ta đã nhận một request khác. Lát nữa ta sẽ thêm mã vào khối else để phản hồi mọi request còn lại.

Hãy chạy mã ngay bây giờ và yêu cầu 127.0.0.1:7878; bạn sẽ nhận được HTML trong hello.html. Nếu gửi bất kỳ request nào khác, chẳng hạn 127.0.0.1:7878/something-else, bạn sẽ gặp lỗi kết nối giống như khi chạy mã ở Listing 21-1 và Listing 21-2.

Giờ hãy thêm đoạn mã ở Listing 21-7 vào khối else để trả về một response với mã trạng thái 404, báo hiệu không tìm thấy nội dung cho request. Ta cũng sẽ trả về một ít HTML cho một trang để trình duyệt render, cho người dùng cuối biết kết quả.

Ở đây, response của ta có status line với mã trạng thái 404 và reason phrase NOT FOUND. Body của response sẽ là HTML trong file 404.html. Bạn cần tạo file 404.html nằm cạnh hello.html cho trang lỗi; một lần nữa, bạn cứ dùng HTML nào tùy thích, hoặc dùng HTML ví dụ ở Listing 21-8.

Với những thay đổi này, hãy chạy lại server. Yêu cầu 127.0.0.1:7878 sẽ trả về nội dung của hello.html, còn mọi request khác, chẳng hạn 127.0.0.1:7878/foo, sẽ trả về HTML báo lỗi từ 404.html.

Tái cấu trúc

Lúc này, hai khối if và else lặp lại khá nhiều: cả hai đều đọc file và ghi nội dung file vào stream. Khác biệt duy nhất là status line và tên file. Hãy làm mã gọn hơn bằng cách tách những khác biệt đó ra thành hai dòng if và else riêng, gán giá trị của status line và tên file vào biến; sau đó ta dùng những biến này một cách vô điều kiện trong phần mã đọc file và ghi response. Listing 21-9 cho thấy kết quả sau khi thay thế hai khối if và else lớn.

Giờ hai khối if và else chỉ trả về giá trị phù hợp cho status line và tên file dưới dạng một tuple; rồi ta dùng destructuring để gán hai giá trị đó vào status_line và filename bằng một pattern trong câu lệnh let, như đã bàn ở Chương 19.

Phần mã trước đây bị lặp giờ nằm ngoài hai khối if và else và dùng hai biến status_line và filename. Nhờ vậy dễ thấy khác biệt giữa hai trường hợp hơn, và ta chỉ còn một chỗ duy nhất cần sửa nếu muốn thay đổi cách đọc file và ghi response. Hành vi của mã ở Listing 21-9 sẽ giống hệt mã ở Listing 21-7.

Tuyệt vời! Giờ ta đã có một web server đơn giản gọn trong khoảng 40 dòng mã Rust, phản hồi một request bằng một trang nội dung và phản hồi mọi request khác bằng một response 404.

Hiện tại server của ta chạy trong một thread duy nhất, nghĩa là mỗi lúc chỉ phục vụ được một request. Hãy xem điều đó có thể thành vấn đề ra sao bằng cách mô phỏng vài request chậm. Sau đó ta sẽ sửa để server xử lý được nhiều request cùng lúc.
